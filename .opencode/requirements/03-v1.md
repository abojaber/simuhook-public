# Phase 03 — V1

> Should-have features. Post-MVP enhancements.

---

## WS-006 — Dynamic payload templating

**Status:** `draft` | **Priority:** `[Should]`

**User Story:**
> As a developer, I want the response payload to support Go template variables (e.g. `{{.Timestamp}}`, `{{.RequestID}}`) so that each webhook response feels realistic and dynamic.

**Acceptance Criteria:**
```
Given an endpoint with body: '{"id":"{{.UUID}}","time":"{{.Now}}"}'
When  a request arrives
Then  the response body contains a fresh UUID and timestamp for each request
```


## WS-007 — Response variability (random / round-robin)

**Status:** `draft` | **Priority:** `[Should]`

**User Story:**
> As a developer testing error scenarios, I want to configure multiple possible responses (success, failure) with weighted probability or round-robin rotation so that I can test error handling paths.

**Acceptance Criteria:**
```
Given an endpoint with two responses: 200 (80%) and 500 (20%)
When  100 requests are sent
Then  approximately 80 return 200 and 20 return 500
```


## WS-008 — Webhook replay from logs

**Status:** `draft` | **Priority:** `[Should]`

**User Story:**
> As a developer debugging an integration, I want to replay a previously received webhook from the logs so that I can reproduce an issue without the real service.

**Acceptance Criteria:**
```
Given a log entry with a specific request payload and headers
When  I run `webhooker replay <log-entry-id>`
Then  the same payload and headers are sent to the configured target
```


## WS-009 — Request match conditions

**Status:** `draft` | **Priority:** `[Should]`

**User Story:**
> As a developer, I want to match webhook requests based on header values or query parameters so that I can simulate endpoints that behave differently based on request context.

**Acceptance Criteria:**
```
Given an endpoint with match condition: header X-Signature exists
When  a request arrives without X-Signature header
Then  the server responds with 400 and a relevant error message
```
