# Architecture

## Overview

Simuhook is a mock HTTP server written in Go. Users define endpoints as YAML files in a `stubs/` directory. The server watches the directory, matches incoming requests against the stubs, and returns configured responses. Stub changes are hot-reloaded live without restart. Every request is logged as a JSON line, and an optional full-screen TUI dashboard shows live stats.

## Commands

- `simuhook` — single command. Flags:
  - `--addr :8080` — listen address (env `PORT`)
  - `--stubs ../stubs` — stubs directory (env `STUBS_DIR`)
  - `--log-dir logs` — log directory (env `LOG_DIR`)
  - `--proxy /path=https://destination` — transparent proxy rule (repeatable, env none): when no stub matches a request whose path starts with `/path`, forward it verbatim to the destination and return the upstream response unchanged. Longest prefix wins; `/` is a catch-all. (Phase 20)
  - `--tui auto|on|off` — dashboard mode. `auto` (default): TUI on a TTY, line output otherwise.
  - `--max-log-body N` (default 0 = unlimited, env `LOG_MAX_BODY`) — caps `body`/`response_body` length in `LogEntry` at capture time (rune-safe truncation); never affects the actual HTTP response bytes or echo/template rendering
  - `--help`, `--version` per CLI conventions

Dependency direction: `main → dashboard → mock`. Nothing in `mock` imports `dashboard` or `main`.

## API

The server exposes only the mock surface: requests are matched against stubs and answered with the configured response. Matched and unmatched requests are both logged.

## Data Flow

1. YAML stubs loaded from `stubs/` at startup; watcher hot-reloads changes live
2. HTTP server binds early (`net.Listen` before any UI output — fail fast on port conflicts)
3. Incoming requests matched against stubs (method, path, headers, query, body)
4. Matched requests get configured response (status, headers, body, optional delay, echo/template modes)
5. Every request logged as a JSON line to `logs/<webhook-id>.log`; unmatched go to `logs/_unmatched.log`
6. `StatsTracker.RecordRequest` updates counts + latency aggregations; the dashboard polls via `Snapshot()`

## Key Decisions

### WS-010 — Interactive TUI dashboard (`[Could]`, done)
- **Framework:** bubbletea v1.3.10 + lipgloss v1.1.0 + bubbles v1.0.0 (viewport only — no list/textinput). First external UI dependency; approved to override stdlib-first for UI only.
- **`--tui auto|on|off`**: `auto` detects a TTY (`golang.org/x/term.IsTerminal`); non-TTY falls back to the WS-016 per-request line output. **No breaking change:** line output and startup banner remain when TUI is disabled; `--tui on` forces the TUI even on a non-TTY.
- **Live updates — fixed 1s poll:** the dashboard refreshes on a fixed 1 s `tea.Tick` (`refreshCmd(m.interval)` with `interval: time.Second`): each `tickMsg` re-reads `Snapshot()` and re-renders. There is **no pump goroutine** and `Program.Send` is never used for refresh (corrected 2026-08-05, DASH-003 — the earlier "coalesced signal + pump at ≤10 Hz" description did not match the implementation). `StatsTracker.Notify()` (buffered(1), non-blocking, coalescing) remains defined but is **not consumed** by the dashboard; it is retained as a seam in case a push-based refresh is added later.
- **StatsTracker latency:** exact `Count/Sum/Min/Max` accumulators over ALL requests plus a fixed 92-bucket logarithmic histogram (4 sub-buckets × 23 octaves, 0.01 ms → ~84 s) for an approximate p95 (interpolated, clamped to `[Min,Max]`). `LatencyStats.Avg()` is the single division and is guarded against `Count==0` (no NaN/div-zero).
- **Signal ownership:** in TUI mode bubbletea owns SIGINT/SIGTERM (its `handleSignals` registers `signal.Notify(sig, SIGINT, SIGTERM)`; SIGINT → `InterruptMsg`, SIGTERM → `QuitMsg`). `main.go` therefore does NOT register `signal.Notify` in TUI mode. After `p.Run()` returns (q/Ctrl+C/SIGTERM), `srv.Shutdown(ctx)` drains with a 5 s timeout. Non-TUI mode keeps the explicit `signal.Notify` + `<-done` path.
- **Log redirection:** when TUI is active, `log.SetOutput(<log-dir>/server.log)` so watcher/stub reload messages can't corrupt the alternate screen. Request logs still go to their own files via `logger.Log`.
- **Filtering:** `Filter{Endpoint, Method, Status, Text}` with `ParseFilter` (`ep:`/`method:`/`status:` prefixes + bare text) is pure and tea-free. Applied at render time only; the ring buffer is never mutated. Prompt mode (`/` or `f`) swallows all keys except backspace/enter/esc/ctrl+c; `q` cancels the prompt before quitting. **Space key:** bubbletea v1.3.10 delivers ` ` as `KeyMsg{Type: KeySpace}` (not `KeyRunes`); the prompt handler must accept both, or multi-token filters (`ep:ping status:200`) are impossible to type (fixed + `TestModelPromptSpaceTyping`).
- **Sticky-bottom feed:** `syncFeed()` checks `viewport.AtBottom()` before `SetContent`, re-anchoring to bottom only if the user was following live; manual scroll offsets survive live updates.
- **Status tinting (UXR-001):** `tint(status)` wraps only the status segment in the feed — 2xx green `"76"`, 3xx cyan `"39"`, 4xx yellow `"220"`, 5xx red `"196"`, other muted `"240"`. Pure render.
- **Per-endpoint stats (UXR-002):** endpoints panel rows append `requests: N  p95: X.Xms` from `Snapshot().HitCounts`/`EndpointLatency`; ID padded to 20 chars for column alignment; zero-hit endpoints show `requests: 0`; row order stays sorted by ID.
- **Keys:** `q`/`ctrl+c` quit, `r` refresh, `/`/`f` filter prompt, `enter` apply (or expand row — see UXR-008), `esc` cancel/clear, `c` clear, `e` toggle endpoints panel, `L` pause/resume live-follow, `?` help; feed navigation via **cursor movement** (UXR-018): `↑/k`, `↓/j` move the selection entry-by-entry, `pgup`/`pgdn`/`b`/`space` jump a viewport page, `u`/`ctrl+u`/`d`/`ctrl+d` half a page — all with auto-scroll (`ensureSelectedVisible`), never touching live-follow; `g`/`G` jump to top/bottom of the stream feed (explicit `KeyMsg` handling — see the `g`/`G` bullet below, bubbles' `DefaultKeyMap` doesn't bind them); `h`/`l`/`left`/`right` still fall through to the viewport (horizontal scroll is a no-op on vertical content).
- **Feed row expansion (UXR-008):** `enter` (non-prompt) expands the **selected row** — the selection is the unified `sel` cursor (UXR-018), identical in fits and overflow modes. **The old overflow-mode "selection = top visible line" derivation is removed** (`selectedIdxFromOffset` deleted); no cursor keys or list widget are needed (the "viewport only, no list/textinput" contract is confirmed intact — the cursor remains a plain `int`). Expansion keyed by `LogEntry.RequestID`, survives ticks, auto-clears when the entry leaves the ring or stops matching the filter. Detail lines (request_id, matched, RFC3339Nano timestamp, headers, query, body, RESPONSE section) map to the same entry index, muted with `│` gutter, truncated to width via local `truncPlain` (lipgloss v1.1.0 has no `Truncate`). `esc`/`c` also collapse; collapsing resumes live-follow and re-attaches the cursor to the newest entry (UXR-018). `syncFeed` uses relative-delta correction so an expanded row's offset survives ticks; `WindowSizeMsg` re-pins the expanded summary line.
- **Feed security (UXR-008):** ALL log-derived text rendered in the feed (path, webhook, header keys/values, query keys/values, body) passes through `sanitize()` which maps control chars `<0x20` and DEL to space — request content is attacker-controlled and could otherwise inject ANSI escape sequences into the TUI alternate screen. The selected-row highlight is built **segment-wise** (each segment carries its own `Background`) because wrapping a string containing an inner `\x1b[0m` in a `Background()` style loses the background after the reset.
- **Two-column layout (UXR-009/010/011, Phase 6, `544db99`):** at `width ≥ 100 && height ≥ 14` the dashboard renders the redesigned layout — title row with `[ Pause Stream ]` button (UXR-010), SERVER INFO chips, muted log-dir line, METRICS & LATENCY chips, then two `RoundedBorder` panels at a fixed 40/60 split (`leftTotal = width*2/5`; `rightTotal = width-leftTotal`): left = REGISTERED ENDPOINTS table (Method|Endpoint|Stub|Req|p95) with its OWN `endpointsView` viewport scrolled by `shift+↑/↓` (aliased `K`/`J`), right = LIVE REQUEST STREAM table (Time|Method|Path|Stub|Status). Below the threshold it falls back byte-identical to the legacy vertical layout. All size math lives in one pure `geometry()` (single source of truth) + `applyGeometry()`/`syncEndpoints()`; `headerHeight()` is unchanged. **No focus state** — existing keys always drive the stream viewport. `e` hides the left panel (stream full width); `compactMs`/`compactCount` render Req/p95; `fitBlock` + per-line `truncPlain` guarantee every panel block is exactly its budgeted size (never `MaxHeight` — it clips the border). Filter chip relocates from the endpoints title to the stream title when the left panel is hidden (UXR-007). Colour 39 in wide chrome is reserved for the chip only. `g`/`G` are NOT bound in bubbles v1.0.0's `DefaultKeyMap` (only `PageDown/PageUp/HalfPageUp/HalfPageDown/Up/Down/Left/Right` are) — implemented separately as explicit `KeyMsg` handling in `model.Update` (backlog item `viewport-g-g-bindings`, resolved): `g` → `GotoTop` + pause live-follow, `G` → `GotoBottom` + resume live-follow; pure navigation, does not collapse an active row expansion. Both `ep.Path` and `ep.ID` are sanitized (unauthenticated admin API is an injection vector).
- **Startup order:** `net.Listen` → registry/watcher/load → TUI decision → logger + log redirect → banner (non-TUI only) → mux/server → `dashboard.Run` (blocks) → `srv.Shutdown`.

### UXR-015 — Colorized request detail (`[Should]`, done 2026-08-07)
- **Problem:** every line of `detailLines` (`enter` expansion) and `inspectLines` (`i` inspector) was wrapped wholesale in `styleMuted` — labels, header/query keys, values, and bodies were indistinguishable gray, and the inspector request body was a single-line blob while the response body was pretty-printed.
- **Styles:** 8 new package-level styles in `render.go` — `styleKey` (cyan `39`, non-bold), `styleLabel` (cyan `39` bold), `styleRequestBody` (yellow `220`), `styleResponseBody` (green `76`), and JSON token styles `styleJSONKey` (39), `styleJSONNumber` (220), `styleJSONBool` (213), `styleJSONPunct` (240). JSON string values are **unstyled** (default foreground); there is deliberately no `styleJSONString`. `styleAccent` is NOT reused for keys (it is semantically the chip/prompt colour). Note: feed-content cyan 39 is fine — the colour-39 chip reservation (UXR-009/010/011) applies to panel title rows only, and 39 already appears in feed content via 3xx status tints.
- **Line classification (build-site, not sniffed):** `detailLines`/`inspectLines` tag every emitted line with a `lineKind` (`kindFixed`, `kindKV`, `kindBlockHead`, `kindMuted`, `kindBodyReq/Resp`, `kindJSONReq/Resp`, `kindReqHeader`) and assemble via one shared pure `renderStyledLine`. Fixed fields render `styleLabel(label) + value-default`; header/query lines render `styleKey(key) + value-default` (leading indent unstyled); block headers and the REQUEST header render `styleLabel(whole line)`; `(none)`/`(empty)` placeholders and `(N more …)`/`… truncated` markers stay muted; plain bodies tint the whole rest (`styleRequestBody`/`styleResponseBody`); JSON bodies highlight each content line with `highlightJSON`.
- **Ordering invariant (per line, all surfaces):** `sanitize()` at build time → build the plain line → `truncPlain(line, contentW)` on the PLAIN string → `splitKV` at the first colon (label keeps the colon; `label + rest == line` byte-for-byte, preserving %-14s alignment) → style the segments → prepend the muted `"  │ "` gutter. An ANSI string is never passed to `truncPlain` (the only exception is the pre-existing RESPONSE header truncation, unchanged). No returned line contains a newline, so `feedLineToEntry`/`entryToLine` stay correct (AC14).
- **`highlightJSON`:** pure, tea-free character-scanner tokenizer (NOT regex — RE2 has no lookahead, so key-vs-value distinction requires a scanner). Whitespace verbatim; `{ } [ ] , :` → punct 240; quoted strings scan to the closing unescaped quote (backslash escapes the next byte) and become KEY (39) iff the next non-whitespace char is `:`; numbers `-?[0-9]+(\.[0-9]+)?([eE][+-]?[0-9]+)?` → 220; `true`/`false`/`null` with a word boundary → 213. Anything unrecognized returns the whole line unchanged (whole-line passthrough, never partial highlighting). `isJSONBody(raw)` mirrors `formatBody`'s JSON-path condition exactly (`raw != "" && len(raw) <= maxInspectJSONBytes && json.Valid`), so the highlight decision never disagrees with the pretty-print decision.
- **Surface changes:** `detailLines` keeps a single-line flattened body (sanitized), label renamed `body:` → `request body:`, yellow 220, **no** JSON highlighting. `inspectLines` gains a NEW cyan-bold `REQUEST` section header as its first line (`styleLabel`-wrapped, mirrors RESPONSE minus the status tint — the only structural line-count change); the request body is now routed through `formatBody` (multi-line, stakeholder decision 2) mirroring the response body, with a per-body `isJSONBody` decision; response label renamed `response body:`. Label column widened `%-12s` → `%-14s` throughout both surfaces (stakeholder decision 3). The RESPONSE header keeps its bold-240 + `tint(status)` with the existing degradation path (unchanged, AC11).
- **Truncated JSON lines render unstyled (stakeholder decision 4, AC15):** a JSON content line cut by `capLines`/`plainBody` (ends in `…`) fails the tokenizer and passes through `highlightJSON` unchanged — default foreground, NOT tinted yellow/green, NOT partially highlighted. Documented here and in the TUI dashboard reference.
- **No new dependencies / no flag changes;** mode-2 (WS-016 line output) and the startup banner are out of scope. Tests: `TestHighlightJSON_*`, `TestSplitKV`, `TestDetailBodyYellowLabel`, `TestInspectBodyTintsReqResp`, `TestInspectJSONHighlightBothSections`, `TestDetailHeaderQueryKeyCyan`, `TestFixedLabelsCyanBold`, `TestSanitizeBeforeStyle`, `TestTruncationMarkerNoAnsiCorruption`, `TestPlaceholdersMarkersMuted`, `TestStyledLinesNoNewline`, `TestInspectRequestHeader`, `TestIsJSONBody` (AC16).

### UXR-018 — Unify feed selection: cursor navigation with auto-scroll (`[Should]`, done 2026-08-08)
- **Problem (stakeholder report 2026-08-07):** in overflow mode (more requests than fit the panel) `j`/`↓` **scrolled the list instead of selecting items**, and the highlight was pinned to the **top visible line** (`selectedIdxFromOffset`), so entries in the lower half of the panel were unreachable/not directly selectable. Root cause: two different selection mechanisms split by `feedFits()` — UXR-008's overflow-mode offset derivation vs UXR-014's fits-mode explicit `sel`. **UXR-018 supersedes UXR-014's two-mode split.**
- **Three stakeholder decisions (2026-08-07):** (1) cursor + auto-scroll — `j`/`↓`/`k`/`↑` move a highlight cursor **entry-by-entry** with the viewport auto-scrolling to keep it visible; (2) **no implicit live-follow from cursor-at-bottom**; (3) **one selection model** — the explicit cursor index everywhere.
- **Selection unification (AC7):** `selectedIdx()` = `clampSel(m.sel, len(m.feedEntries))` in BOTH modes (no mode branch); `selectedIdxFromOffset()` **deleted**; `feedFits()` retained **only** as the syncFeed live-anchor guard (doc comment updated — no longer a selection-path concept); the viewport fallthrough (model.go) stripped to a bare `m.view.Update` forward — the sel re-sync and the "resume live-follow on genuine bottom-ward movement" guard are both **deleted** (the literal implementation of decision 2). `renderFeed` is clamp-only — `m.sel = clampSel(m.sel, len(m.feedEntries))`, no scroll at tick time (cursor-follow runs only on navigation keys; a tick-time scroll would violate AC8's "no drag").
- **Cursor movement + auto-scroll (AC1–AC5):** nav keys (`j`/`↓`/`k`/`↑`) and page keys (`pgup`/`pgdn`/`b`/`space`/`u`/`ctrl+u`/`d`/`ctrl+d`; **`f` stays the filter-prompt key**) are intercepted (non-prompt), move `sel` (page = `view.Height-1`, half for the half-page bindings), set `selTouched=true`, call `ensureSelectedVisible()`, and `return m, nil` — they never touch `liveFollow` (AC8) and never reach the viewport fallthrough. Page keys were a stakeholder-approved addition (the deleted fallthrough re-sync would otherwise let them scroll the view while the cursor drifts off-screen). `h`/`l`/`left`/`right` still fall through (horizontal scroll is a no-op on vertical content). AC3 (entry-by-entry) is structural: `sel` indexes entries, `feedEntryToLine[sel]` is the summary line, detail lines map to the same index and are skipped.
- **`ensureSelectedVisible()` (AC5):** scrolls so the selected summary line stays within `[YOffset+margin, YOffset+Height-1-margin]`, `margin = 1` (0 when `Height < 3`); top trigger `line < y+margin` → `SetYOffset(line-margin)`; bottom trigger `line > y+h-1-margin` → `SetYOffset(line-h+1+margin)`. `SetYOffset` clamps internally (bubbles v1.0.0), so fits mode is a natural no-op (maxYOffset 0) — **one code path for both modes**. The trailing `-1` in `feedLineToEntry` is never targeted; bottom-margin math lands exactly on maxYOffset for the last entry.
- **`g`/`G` unconditional cursor jumps (AC9):** `g` → `sel = clampSel(0, n)`, `selTouched = true`, `GotoTop`, `liveFollow = false`; `G` → `sel = clampSel(n-1, n)`, `selTouched = false`, `GotoBottom`, `liveFollow = true` (explicit action — story §5 Q2 resolution). Pure navigation — does NOT collapse an active row expansion.
- **Live-follow semantics (AC8 / decision 2):** `liveFollow` changes **only** via `L`, `G`, and the three collapse paths (enter-collapse, esc, c) — cursor movement never resumes it, even at the newest entry. New field `m.selTouched bool` (default false): `syncFeed`'s live branch gains a live-attach guard `if !m.selTouched && !m.feedFits() { m.sel = clampSel(len(m.feedEntries)-1, len(m.feedEntries)) }` — while passively live-following the cursor rides the newest entry; once the user moves the cursor, ticks do **not** yank it. New helper `attachCursorToNewest()` (sets `sel = last`, `selTouched = false`; does NOT touch liveFollow/viewport — callers do), folded into `L`-resume and the collapse paths. #### MAT-001..004 — Smarter matching (`[Should]`, done 2026-08-08)
- **Path matchers (MAT-001/002):** exactly one of `path` (exact), `path_glob`, or `path_regex` may be set per stub — load-time parse error otherwise. `path_glob` is segment-wise (`**` = 0+ segments, `*` = exactly one segment, `?` = exactly one rune); **in-segment `*` is a load-time parse error (D2)** — only whole-segment `*`/`**` and in-segment `?` are supported. Matching operates on the raw request path (no URL decoding — unchanged). Trailing/leading slashes are normalized **for glob only** (D5, `splitPathSegs` trims them; root/empty → nil; interior empty segments preserved and significant). `path_regex` is Go stdlib RE2, compiled once at load, **not implicitly anchored** (D6 — the user writes `^…$`). Invalid regex → load-time parse error naming the stub ID and pattern. Matching dispatch lives in `ep.matchPath` (`matcher.go`); the free `matchPath` helper was deleted.
- **`payload_contains` (MAT-003):** partial-JSON request-body match. Spec parsed once at load (`parsePayloadContains`) into `Endpoint.PayloadContains any` + unexported `hasPayloadContains` (D3 — distinguishes a literal `null` spec from unset). At most one of `payload`/`payload_contains` — parse error otherwise. Subset semantics in `subset.go`: objects → every spec key present + recursive subset (extra request keys ignored); arrays → order-independent distinct-element matching via `subsetMatchArray`/`subsetArrayRec` **backtracking** (never greedy); scalars → deep equality with float64 cross-type numeric equality (`42 == 42.0`); `null` → matches only a literal `null`; non-JSON request bodies never match. The request body is parsed **lazily, once per `Match` call** (`parsedDo`/`parsedOK` flags) only when a `payload_contains` candidate exists.
- **Specificity ordering (MAT-004):** `Registry.Match` is a single-pass best-match over all candidates (`best`/`better(a,b)`); map iteration order no longer influences the winner. Comparator: path class (exact 0 < glob 1 < regex 2) → glob wildcard weight (**D1:** `**`=2, `*`=1, `?`=0, fewer wins — `/users/*/orders` beats `/users/**`) → load-order `seq` (monotonic `uint64` assigned in `Add`, **preserved on `Update`** so a hot-reload keeps its slot, D8). Method/headers/query/payload constraints are AND-ed BEFORE comparison — a constraint-failing endpoint is not a candidate. Regex-class endpoints have no comparable weight (regex = infinite), so any glob beats any regex.
- **Compile-at-load (MAT-005):** `compileEndpoint` enforces path/payload exclusivity, pre-splits globs + weight, and compiles regexes. Called from `ParseStubFile` (errors wrapped `stub <id>: …`) and `Registry.Add`/`Update` (programmatic safety net; errors wrapped `endpoint <id>: …`, registry left unchanged, seq not bumped on failure). `ErrDuplicate` sentinel (`errors.Is`) lets the watcher distinguish hot-reload updates ("duplicate %s, updating") from genuine load errors (logged `stub: skip`/`parse error` + continue) in both `LoadAll` and `Watch`. Compiled fields are set under the registry write lock before publishing → race-free.
- **Display (MAT-005):** `Endpoint.DisplayPath()` returns the effective pattern (`path` → `path_glob` → `path_regex`) and is used by the startup banner (`main.go`) and both dashboard endpoints-panel rows (`render.go` — wide table `sanitize(ep.DisplayPath())` and the legacy narrow list, now sanitized too).

#### PROXY-001/002 — Transparent forwarding with full-fidelity logging (`[Should]`, done 2026-08-19)
- **Problem:** teams integrate against real third-party webhook APIs (Stripe, GitHub, …). Simuhook mocked the server side but had no way to test how *your* service behaves against a live API while capturing traffic.
- **Decision (D1):** a `--proxy /path=https://destination` flag (repeatable) adds a transparent forwarding fallback. When **no stub matches** (`Registry.Match` returns nil), the longest-prefix `--proxy` rule whose path prefix matches wins (`/` is a catch-all, `MatchProxy` in `proxy.go`); the request is forwarded via `ForwardRequest` (stdlib `http.DefaultTransport`) and the upstream response is returned **unchanged** (status, headers, body). The destination is a base URL: the caller's original path + query are carried over verbatim — no prefix stripping or rewriting (D1 = A).
- **Hop-by-hop handling (RFC 7230 §6.1):** `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade` are stripped before forwarding; `X-Forwarded-For` is appended with the caller's client IP (prior value preserved after the comma).
- **Fidelity logging (D2/D3, PROXY-002):** new **additive** `LogEntry` fields — `raw_headers` (`map[string][]string`, every incoming value, multi-value preserved), `upstream_request` (`UpstreamRequestLog{method,url,headers,body}` — the exact outbound request actually issued after stripping + XFF), `upstream_response` (`UpstreamResponseLog{status,headers,body}` — full upstream reply). The legacy first-value `headers`/`response_headers` fields and ALL TUI surfaces are untouched (D3 = B — no re-type, no breaking change). `ForwardRequest` returns the built outbound `*http.Request` so the handler can log it.
- **Failed round trips (D4):** unreachable destinations still log `upstream_request` (the exact attempt — URL, headers, body) so it's diagnosable from the log alone, plus `response_status` 502 and `"proxy error: …"` body; `upstream_response` is absent. Normal stub-served requests never populate the fidelity fields (proxy-scoped only).
- **Stubs win:** registry matching happens before proxy fallback, so a local stub always beats a proxy rule (`TestHandler_StubTakesPriorityOverProxy`).
- **Design note:** Go's stdlib `net/http` server rejects truly malformed header *lines* (e.g. a header with no colon) at the parser level with a 400 before the handler runs — such requests cannot be captured via `ServeHTTP`. Anyone hitting that edge needs a raw listener-level tee (out of scope, documented in `20-proxy-forwarding.md`). Valid-but-weird values (`Accept: application/json; foo; bar`) and invalid JSON bodies ARE captured verbatim.

#### PROXY-003 — Raw listener-level tee (`[Should]`, design approved 2026-08-21)
- **Problem:** Go's `net/http` parser rejects malformed requests (e.g. a header line with no colon) with a 400 *before* the handler runs — nothing is logged. PROXY-002's structured `LogEntry` cannot capture what it never sees.
- **Decision:** wrap `net.Listener` with `RawTeeListener` (src/mock/rawtee.go) so every accepted connection's `Read()` AND `Write()` pass through a tee on the way to Go's parser. When the first request-line path starts with a `--proxy` prefix (D1 = path-based capture), all bytes read (`>>>` request) and written (`<<<` response) are appended verbatim to `<log-dir>/_raw.log`. Go's 400 response to a malformed request is also captured — the debugging user sees both the bad request AND the rejection.
- **D1–D6 locked:** path-based capture (D1), auto-on with `--proxy` — no new flags (D2), plain text dump with directional markers (D3), 64 KB per-connection cap shared across request+response (D4), request AND response capture (D5 = B, revised from request-only), decide once per connection from first request line (D6).
- **Types:** `RawTeeListener` (wraps `net.Listener`, `Accept()` wraps conns), `RawTeeConn` (wraps `net.Conn`, intercepts `Read()` + `Write()`), `rawTeeSink` (mutex-guarded append to `_raw.log`, lazily opened, fail-open). 8 KB request-line parse budget for the capture decision; 64 KB per-connection cap (shared request+response). Per-connection mutex for Read/Write concurrency; shared sink mutex for cross-connection file writes.
- **main.go wiring:** 5-line guard before `mux := http.NewServeMux()`: `if len(proxyRules) > 0 { rtl := mock.NewRawTeeListener(ln, proxyRules, *logDir); defer rtl.Close(); ln = rtl }`. Mock-only runs never wrap (D2).
- **12 tests:** well-formed proxy request captured, malformed header+400 captured (raw TCP), non-proxy path not captured, no-proxy identity, fragmented reads, 64 KB cap, budget exceeded, concurrent Read/Write under `-race`, keep-alive inherits, no-proxy no-wrap, concurrent sink writes, non-printable hex-escaped.
- **Limitations (documented, accepted):** keep-alive decision inherited from first request line (D6); 8 KB budget can be forced by adversarial client; 64 KB cap shared (large request may exhaust before response); single `_raw.log` file (serialized writes); no TLS (plain HTTP only); no HTTP/2; `<<<` shows Go's wire output (may include server-added headers like `Date`).
